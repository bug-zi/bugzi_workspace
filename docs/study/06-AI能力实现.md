# 06 - AI 能力实现

> 目标：理解 LLM 客户端、MCP 客户端两个"引擎"，以及架在它们之上的四个业务流程。读完你应能独立加一个新的 AI 功能。

## 1. AI 层的三个文件与依赖方向

```
electron/ai/
├── llm.ts        最底层：OpenAI 兼容 HTTP 客户端（不知道任何业务）
├── mcp.ts        最底层：MCP 协议客户端（不知道任何业务）
└── services.ts   业务层：四个流程，组合 llm/mcp + db/files
                      ↑
               ipc.ts 只 import services 层（和 llm 的测试函数）
```

分层规则：**llm.ts/mcp.ts 不 import db**（纯协议客户端可单测可复用），业务编排全在 services.ts。唯一例外是 llm.ts 读了 settings 拿配置——配置获取被包在 `getDefaultLlm()` 里，算可容忍的 pragmatic 妥协。

## 2. LLM 客户端（llm.ts）

### 配置解析 getDefaultLlm（llm.ts:13-20）

```
settings.llm_configs (JSON数组) + settings.llm_default_id
  → 找 id 匹配默认项；找不到默认 id 就取数组第一个
  → 数组空 → throw LlmNotConfiguredError('LLM_NOT_CONFIGURED')
```

`LlmNotConfiguredError` 是**哨兵错误**：业务层不 catch，让它一路穿透到渲染层，前端拿 message 分流弹「去配置」。这个设计让"未配置"成为全局统一语义，每个调用点不用重复判断。

### URL 规范化 normalizeChatUrl（llm.ts:23-28）

用户在个人中心填的 apiUrl 可能是三种形态，统一拼成完整端点：

```
'https://api.x.com'                → .../v1/chat/completions
'https://api.x.com/v1'             → .../v1/chat/completions
'https://api.x.com/v1/chat/completions' → 原样
```

用户体验意图：**怎么填都能用**。三条正则分支处理"有没有版本段/有没有端点段"的组合，尾斜杠先剥掉。

### chatCompletion（llm.ts:42-76）

标准 OpenAI chat/completions POST：`Authorization: Bearer <key>`，body 含 model/messages/stream:false，可选 temperature 和 `response_format: {type:'json_object'}`（jsonMode）。

错误处理三层：
- fetch 网络异常 → 包装成 `网络请求失败：<原因>`
- HTTP 非 2xx → `LLM 服务返回 <status>：<响应体前300字>`（截断防刷屏）
- 200 但结构不对（无 choices[0].message.content）→ 明确报"格式异常"

**没有重试、没有超时控制、没有流式**——v1 的克制。除格言生成的单次重试外（见下），失败即抛给 UI。

### testLlmConnection（llm.ts:79-102）

个人中心「测试连接」用：发 `max_tokens:1` 的最小请求，只看 HTTP 是否 2xx。省 token 的探活设计。

## 3. MCP 客户端（mcp.ts）——手写的最小协议栈

MCP（Model Context Protocol）：让 LLM 应用调用外部工具的标准协议。本项目只用到**搜索工具**这一个用途（辩真阁联网检索），v1 只支持 **Streamable HTTP 传输**（个人中心配置也只有 名称+地址+开关 三字段）。

### 协议时序（McpSession 类，mcp.ts:22-110）

```
POST <url>  {"jsonrpc":"2.0","id":1,"method":"initialize", params:{protocolVersion,clientInfo}}
   ← 响应头可能带 mcp-session-id（记下来，后续都带上）
   ← 响应体可能是 JSON，也可能是 SSE（text/event-stream）→ parseSseResponse 解析
POST <url>  {"jsonrpc":"2.0","method":"notifications/initialized"}   ← 通知，无 id，不期待响应
POST <url>  {"method":"tools/list"}     ← 拿工具清单
POST <url>  {"method":"tools/call", params:{name, arguments}}  ← 调用工具
```

实现细节值得学的三处：

1. **双格式响应兼容**（rpc 方法，mcp.ts:56-60）：Streamable HTTP 规范允许服务器用 JSON **或** SSE 回。代码按 `content-type` 分流，SSE 走 `parseSseResponse`——逐行找 `data:` 前缀、跳过 `[DONE]`、解析第一个合法 JSON。
2. **会话头透传**：`mcp-session-id` 从 initialize 响应头捕获，后续每个请求（含 initialized 通知）都带上。
3. **容错边界清晰**：initialize 的通知失败静默容忍（协议允许）；单个 MCP 服务器失败在 `findSearchTool` 里跳过试下一个。

### 工具发现 findSearchTool（mcp.ts:130-146）

遍历所有启用的 MCP → listTools → **按名字启发式匹配**：`/search|query|fetch/i.test(t.name)`。取第一个命中的。这个启发式是 v1 的务实解（不搞工具语义分析），隐含约束：**你的 MCP 搜索工具名字里得有 search/query/fetch**。

## 4. 业务流程一：AI 边栏对话 aiChat（services.ts:41-56）

```
appendAiMessage('user', ...)          ← 用户消息先落库（即使后面失败也留痕）
history = 全部消息(排除system).slice(-30)   ← 上下文窗口：最近30条
system = 模块感知提示词（"用户当前所在模块：格言库…"）
chatCompletion([...system, ...history], temperature=0.8)
appendAiMessage('assistant', ...)     ← 回复落库
```

**模块感知的实现朴素到感人**：就是把当前模块中文名塞进 system prompt，靠 LLM 自己理解"围绕该模块优先帮忙"。没有 RAG、没有工具调用，v1 的边栏是纯对话。

## 5. 业务流程二：格言生成 generateMottos（services.ts:81-130）

全流程拆解（这是学习"LLM 结构化输出处理"的最佳样本）：

```
① 取风格样本：正式区最新50条 → "- 内容 —— 出处" 文本
② 构造 prompt：参考风格生成10条，JSON数组格式，编撰的标「AI 编撰」
③ chatCompletion(temperature=0.9, jsonMode=true)
④ parseJsonArray：
     剥 ```json 围栏（正则剥头尾）
     JSON.parse
     逐项校验 content/source 都是 string 才收
     空 → throw
⑤ 失败自动重试一次（仅一次，再失败抛给 UI）
⑥ 查重入库：
     existing = 三区全部格言的 normalizeText 集合
     逐条：key = normalizeText(content)
       空串/已存在/本批重复 → 跳过
       否则 INSERT status='draft', origin='ai'
⑦ 返回 { generated: LLM给的条数, inserted: 实际入库条数 }
```

**normalizeText（db.ts:142-147）是查重的灵魂**：去空白 + 把中英文标点全部剥掉 + 转小写。这样「知行合一。」「知行合一」「知行合一,」被视为同一条。**为什么不在 SQL 里查重**：标点归一化用 JS 正则最顺手，SQLite 里写等价函数成本高，所以选择**全量拉到内存做 Set 比对**——格言量级（个人库几百条）下完全可行。

toast 文案「本次生成 X 条，去重后入库 Y 条」直接暴露两数之差，用户能感知 AI 又重复了自己收藏——诚实的产品细节。

## 6. 业务流程三：知识卡片生成 generateWikiCard（services.ts:141-190）

两模式：

**随机模式**（term 为 null）：
```
随机挑一个板块 → 把已有词条名列成"避开清单" →
LLM 只生成一个词条名（temperature=1.0，剥引号书名号）→
再走下面的通用路径
```
两段式（先名字后卡片）是**成本与质量的双重考虑**：名字若不满意可以在查重处拦截，不会浪费整张卡片的生成。

**通用路径**：
```
查重（term 精确匹配未删词条）→ 重复 throw 'CONFLICT:<词条名>'
    ↓ ipc.ts:231-239 捕获 CONFLICT 前缀 → 转成 {ok:false, conflict} 返回（不是异常！）
固定模板 prompt（# 词条 / ## 一句话定义 / ## 详细解释 / ## 举例 / ## 启示）
    ↓
剥 ```markdown 围栏
    ↓
正则抽「## 一句话定义」段第一行 → summary（列表展示用）
    ↓
INSERT 行（md_path 先 'PENDING'）→ 拿 id → UPDATE 真路径 → mdWrite 写文件
```

**CONFLICT 走返回值不走异常**是这个通道的特殊约定：查重冲突是**正常业务分支**（UI 要展示"已有词条，是否查看"），不是错误。渲染层 `r.ok ? ... : setConflictTerm(r.conflict)`（WikiModule.tsx:103-116）。对比：LLM 网络失败才是异常。**正常分支用返回值、失败用异常**——这条分界线全项目一致。

## 7. 业务流程四：辩真验证 runVerification（services.ts:200-278）

最长流程，三段式 + 全程进度推送（onProgress 回调最终接到 AI 边栏）：

```
findSearchTool(onProgress)              ← 没有可用搜索工具 → throw
    ↓
LLM① 生成3组检索关键词（temperature=0.5，按行切、trim、滤空、取前3）
    ↓
逐组 mcp.callTool(tool, {query: kw})   ← 单组失败 onProgress 告知但继续
   全部失败才 throw '全部检索失败'
    ↓
LLM② 综合分析（temperature=0.3）
   prompt 要求：引用资料说依据 + 末尾单独一行「可信度：N%」
    ↓
正则 /可信度[：:]\s*(\d{1,3})\s*%/ 抽数值，clamp 0-100，抽不到默认 50
   同时从正文里把可信度行删掉（存进独立字段 credibility）
    ↓
INSERT verify_records（md_path 'PENDING'→回填）→ mdWrite 模板文档
    ↓
onProgress('验证完成，可信度 N%')  →  return {recordId, credibility}
```

三个设计点：

1. **可信度用输出协议解析而非结构化输出**：让 LLM 在自然文末尾写 `可信度：N%`，正则抽。比 jsonMode 更适合"主体是长文、附带一个数值"的场景。
2. **temperature 阶梯**：关键词 0.5（要稳定覆盖）、分析 0.3（要严谨）；对比格言 0.9、词条名 1.0（要发散）。**temperature 是按任务性质逐处调的，不是全局一个值**。
3. **md 文档结构**：`# 验证：<观点> / **可信度：N%** / ## 分析 / ## 来源（检索关键词列表）`——分析里的资料链接由 LLM 以 Markdown 链接输出，渲染时被 MdDialog 拦截转系统浏览器（03 篇讲过的安全链）。

## 8. 「未配置」体验的全链路（规则 7 的实现）

```
用户点「来10条格言」（按钮永远不 disabled）
  → invoke mottos:generate
  → getDefaultLlm() throw LlmNotConfiguredError('LLM_NOT_CONFIGURED')
  → 渲染层 catch，msg.includes('LLM_NOT_CONFIGURED')
  → setGoConfig(true) → GoConfigDialog 弹出
  → 「去配置」→ onGoConfig → 模块通知 App 切到 profile 模块
```

MCP 版本同理（`McpNotEnabledError` → 'MCP_NOT_ENABLED'）。**配置检测发生在尝试时而非界面上**——这就是"按钮不置灰"规则的技术底气：反正点了会得到清晰引导。

## 9. 如何新增一个 AI 功能（方法论总结）

以"给灵感泉加 AI 补全描述"为例，照抄既有模式六步：

1. `services.ts` 写业务函数：构造 prompt → `chatCompletion` → 处理输出 → 落库/写 md。
2. 未配置场景：**什么都不用做**，`chatCompletion` 内部第一个 `getDefaultLlm()` 自动抛哨兵。
3. `ipc.ts` 注册 `ipcMain.handle('inspirations:aiExpand', ...)`。
4. `preload.ts` 对应命名空间加方法；**同步** `api.d.ts`。
5. 模块组件：`try { await window.api... } catch (e) { msg.includes('LLM_NOT_CONFIGURED') ? setGoConfig(true) : setFailMsg(msg) }`。
6. 若是长流程：参数加 `onProgress`，内部调 `pushAiSystemMessage` 让边栏直播进度。

## 10. 新人练习

1. 把 `generateMottos` 的 prompt（services.ts:89）复制出来丢给任意 LLM 网页版，观察它返回的 JSON 是否稳定可解析；然后故意要求它"不要用 JSON"看 parseJsonArray 抛什么——体会重试逻辑存在的意义。
2. 读 `parseJsonArray`（services.ts:60-73）的两条 replace 正则，解释它们如何兼容「```json\n[...]\n```」和「裸数组」两种返回。
3. 思考题：为什么格言生成查重用 normalizeText 而 wiki 查重用 term 精确等值？（格言正文可能被用户/AI 写出标点差异，模糊匹配提升查全；词条名是"标题"性质，模糊归一会把「博弈论」和「博弈论。」当成同一个——标题必须精确唯一，正文只需去重近似。**同一机制在不同数据形态下选择不同精度**。）
