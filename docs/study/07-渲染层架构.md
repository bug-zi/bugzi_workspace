# 07 - 渲染层架构

> 目标：掌握 React 代码的组织方式、双主题系统实现、三栏布局、全局组件的复用设计。读完你应能新增一个页面级交互而不错位。

## 1. 组件树全景

```
renderer.tsx
└─ <App>                                    src/App.tsx
   ├─ <ThemeProvider>                       主题/设置/背景 Context（最外层）
   │  └─ <ToastProvider>                    toast Context
   │     └─ <Shell>                         ★ 三栏布局 + 模块路由 + 边栏状态
   │        ├─ .app-bg                      全窗背景图层（div，非组件）
   │        ├─ <nav .sidebar>               六模块按钮 + 主题切换
   │        ├─ <main .main-area>            当前模块组件（条件渲染）
   │        │   ├─ <MottosModule onOpenAi bumpAi/>
   │        │   ├─ <WikiModule .../>
   │        │   ├─ <InspirationsModule/>
   │        │   ├─ <VerifyModule .../>
   │        │   ├─ <RecycleModule/>
   │        │   └─ <ProfileModule/>
   │        └─ <AiSidebar collapsed ... />  右侧边栏
   └─ <WelcomeGuide>                        首启引导（firstLaunch 时）
```

**模块路由 = 一个 useState**（App.tsx:37）：`const [module, setModule] = useState<ModuleId>('mottos')`，主栏里六行条件渲染。没有 URL、没有 history——桌面 App 无路由需求，这是对"网页思维"的自觉抵抗。

## 2. Shell 层的三个跨模块协调（App.tsx 的核心价值）

Shell 不只是布局，它是**唯一**能协调"模块 ↔ 边栏"的层：

### ① openAiWith —— 模块请求打开边栏（可能带预填文本）

```ts
const openAiWith = useCallback((prefill?: string) => {
  setAiCollapsed(false)              // 展开边栏
  setAiForceOpen((v) => !v)          // 触发一次强制展开信号
  if (prefill) setAiPendingAsk(prefill)  // 预填问题
}, [])
```

用户故事：万象库划词点「问 AI」→ WikiModule 调 `props.onOpenAi('解释一下「边际效应」')` → 边栏展开 + 输入框预填。**数据自下而上（props 回调），状态归边栏所有**。

### ② bumpAi —— 通知边栏"消息有更新"

模块内收到 `ai:message` 推送时（如辩真阁验证进度），调 `props.bumpAi()` → Shell 的 `aiVersion+1` → 传给 AiSidebar 的 `messagesVersion` prop → 边栏 useEffect 重载消息。**模块和边栏谁都不直接持有对方引用，全靠 Shell 中转**。

### ③ onNavigateToProfile —— 边栏「去配置」跳个人中心

`GoConfigDialog` 的落地动作最终要"切换模块"，而 setModule 只在 Shell 手里，所以一路回调上浮。

这套"回调上浮 + 状态集中 Shell"的模式，就是没有状态库时的标准解法。代价是 App.tsx props 密集；收益是数据流向一目了然。

## 3. 双主题系统（规则 2 的实现）

### CSS 变量 + data-theme 属性（global.css:6-43）

```css
:root { --font-size:15px; --sidebar-width:76px; ... }     /* 与主题无关的尺寸变量 */

:root[data-theme='light'] {                                /* 樱花粉 */
  --color-primary: #e8a0bf;  --color-text: #1f1f1f;
  --color-surface: rgba(255,255,255,.75);  ...
}
:root[data-theme='dark'] {                                 /* 宝蓝 */
  --color-primary: #1a237e;  --color-text: #ffffff;
  --color-surface: rgba(40,53,147,.55);    ...
}
```

**切主题 = 改 `<html>` 上一个属性**，所有颜色瞬时联动。规则 4「禁止彩亮颜色」的落地方式：全部组件样式只引用 `--color-*` 变量，没有任何组件自己写死颜色（危险色也是主题化的 `--color-danger`：浅色 #b0577d / 深色 #ff8fab）。半透明 surface（rgba .55~.92）让背景图透出来，是"卡片浮在壁纸 上"视觉的来源。

### 字体三件套也是变量（规则：个人中心可调字号/字体/粗细）

`--font-size / --font-family / --font-weight`，body 上消费（global.css:58-63）。个人中心改动 → ThemeProvider.applyFontVars 直接 `root.style.setProperty` 写内联变量——**改设置不需要重渲染 React 树，CSS 变量自己生效**。

### ThemeProvider 的状态职责（ThemeProvider.tsx）

一个 Context 管：theme 切换、背景图 URL 解析与探测、settings 缓存、firstLaunch 判定。

值得看的是 **applyBg 的探测回退**（ThemeProvider.tsx:56-76）：

```ts
const key = t === 'light' ? 'bg_bg-light' : 'bg_bg-dark'
const file = all[key]
url = `bzres://bg/${file}`
const probe = await fetch(url)        // ③ supportFetchAPI 才能这么探测
if (!probe.ok) url = ''               // 404 → 回退
--bg-image = url ? url(...) : 'none'  // none 时 .app-bg 的 background-color 兜底
```

设置里记着文件名 ≠ 文件还在（用户可能手删过）。**每个"配置指向资源"的地方都要有存在性探测**——这是桌面本地应用特有的健壮性问题。

firstLaunch 判定同样朴素：`!all[SettingsKeys.UserName]`（没填过用户名 = 第一次）。onDone 只 setFalse（内存态），持久的"已引导"标记就是用户名本身——**用业务数据当状态位，不另设 flag**。

### toggleTheme 的一个小细节

```ts
const toggleTheme = useCallback(() => {
  setTheme(document.documentElement.getAttribute('data-theme') === 'dark' ? 'light' : 'dark')
}, [setTheme])
```

读 **DOM 属性**而不是 React state 判当前主题——绕开 useCallback 闭包捕获旧值的问题。务实但有点绕（若 setTheme 异步未落 DOM 会连切两次），读代码时知道意图即可。

## 4. 三栏布局 CSS（App.css:1-52）

```
.app-shell { display:flex; height:100% }
  .sidebar    { width: var(--sidebar-width)(76px); flex列 }   ← 固定窄条
  .main-area  { flex:1; min-width:0; overflow-y:auto }        ← min-width:0 是 flex 溢出救星
  .ai-sidebar { width: var(--ai-width)(320px)；收起时 36px }
```

`.main-area` 的 `min-width: 0`：flex 子元素默认 `min-width:auto`，内容宽（长格言不换行）会把整行撑爆导致横向滚动；这一行是 flex 布局踩坑后必写的防守。

模块内部再套 `.module-page { max-width:980px; margin:0 auto }` 居中限宽（灵感泉 1200），内容不随超宽屏摊大饼。

## 5. 全局组件四件套的复用设计

### MdDialog —— 全项目最重的组件（MdDialog.tsx，222 行）

四个模块的文档弹窗共用（格言笔记/万象卡片/灵感文档/辩真记录），通过 props 留差异口：

| prop | 作用 | 谁用 |
|---|---|---|
| `filePath` | md 相对路径（核心） | 全部 |
| `onChanged` | 保存后回调（列表刷新） | 格言/灵感/万象 |
| `selectionActions` | 划词气泡开关 | **仅万象**（高光+问AI） |
| `onTitleChange` | 头部标题可编辑 | **仅灵感**（标题改后列表同步） |

**渲染/编辑双态**是它的灵魂：

```
默认：md → marked.parse → DOMPurify.sanitize → innerHTML
      + 后处理：==text== 替换成 <mark>（marked 原生不认 == 语法）
      + 拦截所有 <a> 点击转 window.api.shell.openExternal
双击正文 → startEditing()：textarea 装载原文（不是渲染后的 HTML）
「完成」/Esc/点遮罩 → saveAndExit()：有 diff 才 md.write，退出编辑态
```

**安全链**：AI 生成内容 → DOMPurify 消毒 → 链接拦截出系统浏览器。XSS 双保险。

**划词气泡**（仅 selectionActions 传入时挂载）：document 监听 mouseup → Selection 取文本（≤500字 且 range 落在 body 容器内）→ 动态创建气泡 div 定位在选区上方 → 两个按钮（高光/问AI）→ 冒泡关闭时 removeBubble + removeAllRanges。**用原生 DOM 而非 React 渲染气泡**——因为要精确定位在 window.getSelection 的屏幕坐标上，React 声明式模型反而碍事。组件内"该用 DOM 的地方用 DOM"是合理越界。

### ConfirmDialog —— 规则 1 的执行者

35 行，通用四件：title/children（正文任意 JSX）/confirmText/danger（红色按钮变体）。**每个模块的丢弃按钮 onClick 都只是 `setDiscardTarget(item)`**，弹窗 open 由 target 是否为 null 决定——"先选中目标，再弹确认"而非"点击即执行"。所有删除路径无一例外（格言:364、词条、灵感、辩真:213、回收站彻底删:142）。

### GoConfigDialog —— 规则 7 的执行者

kind: 'llm'|'mcp' 两文案；「去配置」按钮回调由调用方注入（最终上浮到 Shell 切模块）。

### Toast —— 极简 Context 版

`useToast()` 拿 `toast(text)`；2.6s 自动消失；Provider 里 setTimeout 过滤 id。没有动画库、没有队列上限——够用就好。

## 6. 模块组件的通用解剖学

六个模块共享同一个骨架（以 MottosModule 为例，其他都是变体）：

```tsx
// 状态分四组，几乎每个模块都能对号入座：
const [items, setItems] = useState(...)        // ① 列表数据
const [viewId, setViewId] = useState(...)      // ② MdDialog 目标
const [editing, setEditing] / [adding, setAdding] / ...  // ③ 各弹窗开关+草稿
const [discardTarget, setDiscardTarget] / [goConfig] / [failMsg]  // ④ 三种异常流程目标

const load = useCallback(async () => setItems(await window.api.xxx.list()), [])
useEffect(() => { void load() }, [load])       // 挂载加载

// 每个动作：await api → toast → load() 刷新
```

**弹窗即 state**：没有 Modal 管理器，一个布尔/目标值一个弹窗，条件渲染 `{editing && <div className="dialog-overlay">…}`。所有弹窗共用 `.dialog-overlay / .dialog / .dialog-header/-body/-footer` 样式类（App.css），所以视觉统一靠 CSS 类而非组件继承。

各模块的特色差异一览（走读时的地图）：

| 模块 | 特色机制 | 所在行 |
|---|---|---|
| 格言 | 三区折叠面板、批量导入文本解析、定时设置 | MottosModule.tsx:102-133 |
| 万象 | 三视图（总览/板块页/笔记本）View 判别联合、conflict 分支 | WikiModule.tsx:14,98-124 |
| 灵感 | HTML5 拖拽（跨区/区内排序/sort 归一化） | InspirationsModule.tsx:58-105 |
| 辩真 | Ctrl+Enter 提交、重复检测三选一弹窗 | VerifyModule.tsx:48-58,169-202 |
| 回收站 | 四页签、remainText 存活文案、payload 摘要 | RecycleModule.tsx:17-37 |
| 个人中心 | LLM/MCP 配置编辑、字体设置、头像上传 | ProfileModule.tsx |

灵感泉的拖拽值得一提（InspirationsModule.tsx:80-105）——**区内排序用 `target.sort - 0.5` 插中缝**：拖到某卡片"前"就把 sort 设为目标值减 0.5，再 normalizeSort 把全区重编为 0..n 整数。用浮点中缝避免"要重排后续所有元素"的当场计算，是简洁的经典手法。

## 7. 依赖数组与 effect 的两个易错点（读代码时留意）

1. **load 的依赖**：`useCallback(..., [])` 空依赖 → 引用稳定 → `useEffect(..., [load])` 只跑一次。如果 load 依赖了 state，就会链式重跑造成循环刷新。当前代码全靠"load 内只调 api 不读 state"保持干净。
2. **VerifyModule 的 aiVersion 转发**（VerifyModule.tsx:43-46）：

```ts
useEffect(() => {
  if (aiVersion > 0) props.bumpAi()
}, [aiVersion, props])
```

依赖里放了 `props`（对象每渲染都新建）→ 这个 effect 每次渲染都跑，靠 `aiVersion > 0` 的守卫才不轰炸。**这是全项目最脆的一处 effect**（功能正确但依赖不纯），读代码时要能识别，写新代码时要避免（应当解构 props.bumpAi 单独进依赖）。

3. 思考题：为什么 ToastProvider 在 ThemeProvider 内层而不是外层？（Toast 渲染的内容不依赖主题 Context…… 其实无所谓——真正的原因只是"谁都不需要"，层级顺序在这对组合里是自由度；但 ThemeProvider 必须最外，因为所有组件都可能消费主题。**Context 层级由消费关系决定，无关的随意**。）
