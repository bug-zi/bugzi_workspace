# 05 - 数据存储设计

> 目标：掌握双存储模型（SQLite + md 文件）、每张表的字段意图、回收站的数据机制、路径安全。读完你应能回答"任何一条数据住在哪、活多久、怎么没的"。

## 1. 双存储模型：什么进 DB，什么进 md

总原则写在 CLAUDE.md：**结构化数据存 SQLite，文档性内容存真实 .md 文件**。判断标准是"你要不要对它做查询/过滤/排序"：

| 数据 | 存储 | 理由 |
|---|---|---|
| 格言列表（content/source/status） | SQLite `mottos` 表 | 要按区过滤、查重、统计 |
| 格言的**笔记文档** | `md/mottos/<id>.md` | 长文自由编辑，只有正式区有 |
| 万象词条（term/summary/板块归属） | SQLite `wiki_entries` | 要按板块查、查重 |
| 知识卡片正文 | `md/wiki/<id>.md` | 固定模板长文 |
| 灵感（title/status/sort） | SQLite `inspirations` | 看板排序查询 |
| 灵感专属文档 | `md/inspirations/<id>.md` | 长文 |
| 辩真记录（claim/可信度） | SQLite `verify_records` | 列表+查重 |
| 验证分析全文 | `md/verify/<id>.md` | 长文 |
| AI 会话消息 | SQLite `ai_messages` | 按序读全部 |
| 设置（含 LLM/MCP 配置 JSON） | SQLite `settings` | 键值 |

**md 文件名 = DB 行 id**（`3.md` 对应 id=3 的行）。DB 是索引和真相，md 是内容体。

一个微妙点：**md_path 字段先插 PENDING 再 UPDATE**（ipc.ts:265-268）——因为 id 是自增的，插入前不知道，只能先插拿到 id 再回填路径。看到 md_path 值为 `'PENDING'` 的行，说明创建流程中断过（半成品态）。

## 2. userData 目录布局

`initDb()`（db.ts:18-28）首次启动建目录：

```
<userData>/                      ← app.getPath('userData')，Windows 下约
│                                  %APPDATA%/bugzi_workspace
├── bugzi.db                     ← SQLite（WAL 模式）
├── avatar.png                   ← 头像（扩展名随用户上传而定）
├── bg/bg-light.png, bg-dark.png ← 背景图
└── md/
    ├── mottos/<id>.md
    ├── inspirations/<id>.md
    ├── wiki/<id>.md
    └── verify/<id>.md
```

两条 PRAGMA（db.ts:25-26）：
- `journal_mode = WAL`——写不阻塞读，桌面单机应用的标配选择。
- `foreign_keys = ON`——SQLite 默认**关**外键约束，必须显式开（wiki_entries.section_id → wiki_sections.id）。

## 3. 版本化迁移

没有引 migration 库，手写了最小方案（db.ts:30-133）：

```ts
const version = Number((d.prepare('PRAGMA user_version').get() as any).user_version ?? 0)
if (version < 1) {
  d.exec(`CREATE TABLE IF NOT EXISTS ...全部表...`)
  ...种子数据...
  d.exec('PRAGMA user_version = 1')
}
```

- 用 SQLite 内置的 `user_version` PRAGMA 当版本号（专门的用法，不占表）。
- 以后加表/加列就写 `if (version < 2) { ...; PRAGMA user_version = 2 }`，老库自动升级。
- 建表全部 `CREATE TABLE IF NOT EXISTS`，幂等兜底。

**种子数据**两处：五个初始板块（经济学/法学/心理学/博弈论/历史神话）、两个默认设置（theme=light、motto_schedule=22:00）。注意板块种子只在 version<1 的分支里跑——**已有库不会重复插入**，这是把"新用户初始化"合并进"schema 迁移"的做法，简单但有隐含约束（比如以后想让新库初始板块不同，得走新版本号）。

## 4. 全部 9 张表速查

### 业务表 4 张（都有 deleted_at 软删列）

```
mottos            格言
  content          正文
  source           出处（AI 编撰则写「AI 编撰」）
  status           'draft'|'settled'|'formal'  ← 三区就是这一个字段
  note_path        正式区笔记 md 路径（其余区为 NULL）
  origin           'manual'|'ai'               ← 列表上的 AI 徽章
  created_at/updated_at/deleted_at

wiki_sections     万象板块（name UNIQUE）
wiki_entries      万象词条
  section_id → wiki_sections.id
  term / summary（一句话定义）
  md_path / origin('ai'|'manual')
wiki_highlights   划词高光（entry_id, text）   ← 无软删列，随词条彻底删除

inspirations      灵感
  status           'draft'|'project'|'develop'|'archive'  ← 四区一个字段
  md_path / sort   ← sort 支撑区内拖拽排序

verify_records    辩真记录
  claim / analysis / credibility(0-100) / md_path
```

### 基础设施表 5 张

```
settings          key-value（LLM/MCP 配置存 JSON 字符串）
ai_messages       AI 边栏单会话全历史（role/ai_module/content）
recycle_bin       回收站（source/item_id/payload快照/created_at）
```

**三区/四区不是三张/四张表，是一个 status 字段 + 部分索引**（`idx_mottos_status ON mottos(status) WHERE deleted_at IS NULL`）——查询永远 `WHERE deleted_at IS NULL AND status = ?`。状态机流转（草稿→沉淀→正式）就是一行 UPDATE。这是"列上做状态"对"分表做状态"的胜利：**流转零数据搬移**。

## 5. settings 表的"万物皆字符串"设计

`electron/db/settings.ts` 极小（42 行），但有两个值得注意的取舍：

```ts
getSetting(key)                 // → string | null
setSetting(key, value)          // UPSERT（ON CONFLICT(key) DO UPDATE）
getJsonSetting<T>(key, fb)      // JSON.parse 失败回退默认值
```

- **值一律 TEXT**：数字（字号）、布尔（首启）、复杂结构（LLM 数组）全序列化成字符串存。SQLite 是动态类型，这样最省心，代价是读取端要转型。
- **key 常量集中在 `src/shared/types.ts` 的 `SettingsKeys`**（两进程共用，防止手拼字符串拼错）。
- `getJsonSetting` 的**解析失败回退**很重要：LLM 配置 JSON 如果被手改坏，App 不会崩，表现为"未配置"，用户能进个人中心修。
- 特别的一个 key：`last_motto_run`——定时任务的**幂等标记**（今天跑过没有，详见 09 篇）。

## 6. 回收站机制（本项目最精巧的数据设计）

`electron/services/recycle.ts`，四个函数撑起全部语义：

### 入站 discardToRecycle（recycle.ts:33-45）

```ts
UPDATE <业务表> SET deleted_at = ? WHERE id = ?        -- ① 软删
INSERT INTO recycle_bin (source, item_id, payload, created_at)  -- ② 快照
```

**双写**：软删保留原行（恢复时数据零丢失），快照 payload 再存一份原行 JSON。为什么冗余存两份？——防"已删但未入回收站"的中间态：软删的行不再出现在任何业务查询里（都带 `deleted_at IS NULL`），如果只有软删没有快照，回收站列表就得"每行去四张表反查"，且条目被同名恢复+再删后会混乱。快照让回收站**自治**：显示（RecycleModule 的 `summaryOf` 直接 JSON.parse payload 提 content/term/title/claim）和清理都不依赖业务表。

### 恢复 restoreFromRecycle（recycle.ts:48-72）

各来源规则不同，switch 分派：

| 来源 | 动作 |
|---|---|
| mottos | 清 deleted_at **且 status 重置为 'draft'**（回最初级区） |
| inspirations | 清 deleted_at 且 status='draft' |
| wiki | 只清 deleted_at（回原板块——板块关系从未丢） |
| verify | 只清 deleted_at（回历史列表） |

然后删 recycle_bin 行。注意恢复**直接改原行**，payload 快照此时就完成使命被丢弃——如果原行已被彻底删除，恢复会 UPDATE 一个不存在的 id（无效果无报错），回收站记录倒是被删了。edge case：先恢复同名、原行还在的情况下一切正常。

### 彻底删除 hardDelete（recycle.ts:75-96）

级联清单：wiki 高光（若是词条）→ 业务表 DELETE → recycle_bin DELETE → 附属 md 文件 unlink。**附属 md 在这里才删**——入站时不删（恢复要还给你），彻底删除才真消失。

### 超期清理 cleanupExpired（recycle.ts:99-108）

```ts
SELECT id FROM recycle_bin WHERE created_at <= (now - 3天)
→ 逐条 hardDelete
```

触发时机：**App 启动时一次 + 每天零点**（scheduler 排程，见 09 篇）。注意用的是 ISO 字符串比较——ISO 8601 格式字符串的字典序 = 时间序，SQLite TEXT 比较恰好正确。3 天 = 72h 自然时间，与「剩 N 天」的展示口径（RecycleModule 的 `remainText`）用同一常量逻辑。

### 一个已知的口径问题（学习素材）

`restoreFromRecycle` 把格言恢复到草稿区时**不创建笔记 md**（只有 status 变 draft，note_path 保留）；如果这条格言原本是正式区（有笔记），恢复后变草稿区行但 note_path 还挂着——UI 上草稿区行点击不开弹窗（`m.status === 'formal' && m.note_path` 的条件，MottosModule.tsx:199），笔记文件静静躺着，等它再升回正式区时 `setStatus` 发现 note_path 已存在就不再重复创建（ipc.ts:187-191 的 `!row.note_path` 判断）。**行为自洽，但"草稿区行携带 note_path"是个隐含状态**——读代码时要能看出来。

## 7. md 文件服务与路径安全

`electron/services/files.ts` 是所有 md 操作的唯一出口：

```ts
mdRead / mdWrite / mdDelete / mdCreate / pruneEmptyDir
         │
         └→ resolveUnderUserData(relPath)     ← 每个操作必经
              root = resolve(userDataDir())
              abs  = resolve(root, relPath)
              abs 必须等于 root 或以 root\ 或 root/ 开头，否则 throw PATH_OUT_OF_USERDATA
```

**为什么必须防**：md 路径来自渲染层（IPC 参数），渲染层理论上是可信代码，但 AI 生成的 md 内容、未来任何 XSS 残留都可能尝试传 `../../etc/xxx`。路径校验把"任意文件读写"降级为"userData 内读写"。

细节：
- `mdCreate`：**存在则不覆盖**（保护既有笔记）；`mdWrite`：无条件覆盖（编辑保存用）。
- `mdDelete`：ENOENT 静默（幂等删除）。
- `pruneEmptyDir`：删 md 后清空父目录（当前代码里定义了但主流程未用——遗留工具函数）。
- Windows 感知：startsWith 同时检查 `\\` 和 `/` 两种分隔符（files.ts:10）。

## 8. 事务的缺失（诚实的技术债）

全项目**没有一个显式事务**。多步写操作（如 discard 的 UPDATE+INSERT、verify 的 INSERT+UPDATE+写md）如果中途崩溃会留半成品。对个人单机低写入应用，WAL + 操作短平快使风险很低，但你要知道：**回收站入站若在两步之间断电，会出现"行已软删但回收站没有"的幽灵数据**（表现为：条目从列表消失、回收站也看不到、DB 里 deleted_at 非空）。修复手段就是包一层 `d.exec('BEGIN')...COMMIT`——留作练习。
