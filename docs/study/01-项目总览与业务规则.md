# 01 - 项目总览与业务规则

> 目标：10 分钟搞清楚这个 App「做什么、为谁做、有哪些不可逾越的规则」。

## 1. 产品定位

**「bugzi's workspace」= 生活化个人专属工作台**。关键词逐个拆：

- **生活化**：管理的是「格言、知识、灵感、观点」这类个人精神生活内容，不是工作任务。
- **个人专属**：单用户、无登录、无云同步。装好就是你的，数据在你电脑上。
- **工作台**：六个模块各管一摊，右侧常驻一个感知上下文的 AI 助手。

典型的使用想象：晚上 10 点，App 自动按你正式区格言的风格生成 10 条新格言等你挑；你白天攒的灵感在四区看板里拖着走；看到一个可疑观点丢进辩真阁让它联网查证；读知识卡片时划一句话存进笔记本。

## 2. 六大模块速览

### 格言库（mottos）
- **三级流转**：`draft`（草稿区）→ `settled`（沉淀区）→ `formal`（正式区），只能往上走。
- AI 生成的格言进**草稿区**；手动新增/批量导入进**正式区**。
- 只有**正式区**的格言有独立 md 笔记（`md/mottos/<id>.md`），点击打开弹窗，实时编辑实时渲染。
- 「来10条格言」按钮：取正式区最多 50 条作为**风格样本**喂给 LLM，生成 10 条（每条标出处），规范化查重后入库草稿区。
- 定时生成：默认每晚 22:00（可在 UI 改），**App 未运行时错过即跳过，不补生成**。

### 万象库（wiki）
- 板块（section）→ 词条（entry）两级结构，初始五个板块：经济学/法学/心理学/博弈论/历史神话，可自定义。
- 词条详情是一张固定模板的知识卡片 md：`# 词条 / ## 一句话定义 / ## 详细解释 / ## 举例 / ## 启示`。
- 列表页显示的「摘要」= 从生成的 md 里正则抽出「一句话定义」段的第一行。
- **划词交互**（仅卡片弹窗内）：选中文字 → 浮出气泡 → 「高光」（md 里包 `==标记==` + 存 wiki_highlights 表 → 笔记本板块）或「问 AI」（预填文本 → 展开 AI 边栏）。
- 生成方式两种：随机（AI 先想词条名再生成卡片）或手动输入词条名。

### 灵感泉（inspirations）
- **四区看板**：`draft`（草稿）→ `project`（立项）→ `develop`（开发）→ `archive`（归档）。
- 每个灵感 = 一条 DB 记录（title/status/sort）+ 一个专属 md 文档。
- 支持跨区拖拽（HTML5 Drag & Drop）和右键菜单移动；区内可拖拽排序（sort 字段 + 归一化）。

### 辩真阁（verify）
- 输入一个观点 → 查重（曾验证过则提示查看旧记录/重新验证）→ **三段式自动流程**：
  1. LLM 生成 3 组中英文检索关键词；
  2. 逐组调 MCP 搜索工具检索；
  3. LLM 综合所有检索资料输出分析 + 可信度百分比（0-100）。
- 验证过程实时以**系统消息**推送到 AI 边栏（「正在检索：xxx」），完成后写 verify_records + md 文档。
- 依赖：LLM **和** MCP 都要配好，缺一个点按钮就弹引导框。

### 回收站（recycle）
- 四个页签对应四个来源模块。每条记录是**入站快照**（payload = 原行数据 JSON）。
- 「恢复」规则（回**来源模块的最初级区**）：格言→草稿区、灵感→草稿区、词条→原板块、验证记录→历史列表。
- 「删除」= 彻底删除：DB 行 + 附属 md + wiki 高光 全没了，有二次确认。
- **3 天自动清理**：App 启动时 + 每天零点检查超期条目。

### 个人中心（profile）
- 个人信息：用户名 / 头像 / 个性签名。**没有 user_name 就是首次启动**，会弹欢迎引导（用户名+主题+LLM 提示）。
- App 设置：字体大小/样式/粗细（CSS 变量实时生效）、LLM 配置（多套，OpenAI 兼容）、MCP 配置（多套，v1 仅 HTTP 传输）。

### AI 助手（全局右侧边栏）
- 可收起/展开；自由对话；**模块感知**（system prompt 里注入"用户当前在格言库"）。
- v1 是**单会话全历史持久化**（ai_messages 表，不清理）。
- 兼作**系统消息面板**：辩真阁验证过程、定时生成结果都推到这里。

## 3. 全局硬性规则（「宪法」，改任何代码前先背下来）

来自 `docs/project/需求（功能模块）/总需求文档.md` 与 `docs/project/样式/design.md`：

| # | 规则 | 代码落点 |
|---|---|---|
| 1 | **所有丢弃/删除必须二次确认弹窗** | `ConfirmDialog` 组件，每个模块的 discard 按钮都先 `setDiscardTarget` |
| 2 | 双主题：浅色=樱花粉+黑字，深色=宝蓝+白字；背景用用户上传图 | `src/theme/global.css` 的 `[data-theme]` 变量 + `ThemeProvider` |
| 3 | **禁止 emoji 作图标**，一律用 Material Symbols | `material-symbols` npm 包本地引入 |
| 4 | 组件框/按键/弹窗禁止彩亮颜色，须贴近主题色系 | CSS 全部走 `--color-*` 变量 |
| 5 | 三栏布局：左（模块导航，固定顺序）→ 中（模块内容）→ 右（AI 助手） | `App.tsx` 的 `.app-shell` + `App.css` |
| 6 | md 弹窗为全局统一组件，默认渲染态、双击进编辑态 | `MdDialog` 组件 |
| 7 | LLM/MCP 未配置时按钮**不置灰**，点击弹提示 +「去配置」直达个人中心 | `GoConfigDialog` 组件 |
| 8 | 定时任务错过即跳过 | `scheduler.ts` 的 `alreadyRanToday` 逻辑 |
| 9 | 首次启动有欢迎引导 | `WelcomeGuide`，由「无 user_name」判定 |

注意规则 7 的反直觉之处：常规做法是没配置就把按钮 disabled，这里明确**不让**——因为这是个人工具，配置是顺手的事，不该让界面看起来"坏了"。

## 4. 文档体系（你在哪能找到"为什么这么设计"）

```
docs/
├── project/
│   ├── 需求（功能模块）/
│   │   ├── 总需求文档.md          ← 全局硬性规则出处
│   │   ├── 格言库/design.md       ← 开发者手写的需求（人写）
│   │   ├── 格言库/designs-specs.md ← AI 据 design.md 生成的开发规格（AI 写）
│   │   └── ...（每模块一对）
│   ├── 样式/design.md + designs-specs.md
│   └── idea/                      ← 开发者的点子库，AI 不碰
├── log/260902.md                  ← 开发日志（AI 按天记）
└── study/                         ← 你正在读的这套笔记
```

**工作流**：开发者写 `design.md`（人话需求）→ AI 生成 `designs-specs.md`（结构化开发规格）→ AI 按 specs 写代码。所以**代码里每条逻辑基本都能在某个 specs 里找到条目**，代码注释大量出现 `（specs §3.1）` 这样的引用，那就是回溯需求的线索。

## 5. 新人第一个练习

打开 `src/App.tsx`，找到 `MODULES` 数组（第 16-23 行）。对照规则 5 里的「固定顺序：格言库→万象库→灵感泉→辩真阁→回收站→个人中心」，确认左侧边栏的渲染顺序就是数组顺序。然后思考：如果产品要加第七个模块，**最少**要改哪几个文件？

（答案：`types.ts` 的 `ModuleId` 联合类型、`App.tsx` 的 `MODULES` 数组、`preload.ts`/`api.d.ts` 加 IPC 通道、`ipc.ts` 注册处理器、`db.ts` 建表、新建 `src/modules/xxx/` 组件——这个"扩散面"正是 03/04 篇要讲清的主线。）
