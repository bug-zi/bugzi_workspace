# 02 - 技术栈与工程结构

> 目标：知道每个依赖为什么在 package.json 里，目录按什么逻辑分，日常命令背后发生什么。

## 1. 技术选型一览

| 技术 | 版本 | 用途 | 为什么选它 |
|---|---|---|---|
| Electron | ^44.1.1 | 桌面壳 | 跨平台桌面事实标准；前端技能直接复用 |
| React | ^19.2.8 | 渲染层 UI | 组件化适合"多模块 + 全局组件复用"的形态 |
| TypeScript | ^7.0.2 | 全仓语言 | IPC 两端靠类型对齐，TS 是刚需 |
| electron-vite | ^5.0.0 | 构建器 | 分别打包 main/preload/renderer 三个产物 |
| Vite | ^8.2.2 | 底层构建 | electron-vite 的依赖，带来秒级 HMR |
| node:sqlite | 内置 | 结构化存储 | **Node 22+ 内置模块，零原生依赖**，不用 better-sqlite3（省去原生编译坑） |
| marked | ^18.0.11 | md → HTML | MdDialog 渲染 |
| dompurify | ^3.4.14 | HTML 消毒 | md 渲染前防 XSS（AI 生成内容不可信） |
| material-symbols | ^0.47.0 | 图标字体 | 规则 3：禁 emoji，图标全走这里，本地打包不依赖 Google CDN |

**刻意没用的东西**：没有 Redux/Zustand（状态量小，useState + Context 够了）、没有 react-router（模块切换就是一个 state）、没有 UI 组件库（样式规范强定制，手写 CSS 变量更可控）、没有测试框架（个人项目，typecheck + 人工验收）。

这个"依赖极简"的选型本身就是设计态度：**能用平台内置的不引第三方，能少一层抽象就少一层**。

### 分层的核心原则

**按「进程」分，再按「职责」分**：

- 第一刀：`electron/` vs `src/` —— 这是**进程边界**，也是**能力边界**（能不能碰文件系统）。
- 第二刀：主进程内 `db/`（数据）→ `services/`+`ai/`（业务）→ `ipc.ts`（接口层）；渲染层内 `theme/`+`components/`（横切）→ `modules/`（纵切业务）。
- `src/shared/types.ts` 是**唯一**同时被两个进程 import 的文件——类型与常量（如 `SettingsKeys`）放这里，保证两端对齐。

### 为什么渲染层没有 hooks/api 服务层

模块组件直接调 `window.api.mottos.list()`，没有再包一层 repository。因为 preload 本身就已经是"类型化 API 客户端"了，再包一层纯属转发。等出现"多模块共享同一数据视图"的需求时再抽象不迟。

## 3. 构建配置解读

`electron.vite.config.ts` 定义三个独立构建入口：

```ts
main:     entry: electron/main.ts      → out/main/index.js     （Node 环境，CJS/ESM by electron-vite）
preload:  entry: electron/preload.ts   → out/preload/index.js  （沙箱受限环境）
renderer: root: src/, input: src/index.html → out/renderer/    （浏览器环境，带 React 插件 + @ 别名）
```

注意 `main` 字段指向 `out/main/index.js`（package.json 第 5 行）——Electron 启动的就是它。开发时 electron-vite 会把 renderer 跑成 dev server，主进程通过环境变量 `ELECTRON_RENDERER_URL` 感知（见 `electron/main.ts:40`）。

## 4. 双 tsconfig 的原因

主进程和渲染层的**运行环境完全不同**：

| | tsconfig.node.json | tsconfig.web.json |
|---|---|---|
| 覆盖 | electron/**, src/shared/ | src/**, electron/preload.ts |
| lib | Node 全家桶 | DOM 全家桶 |
| 意义 | 允许 `node:fs`/`node:sqlite` | 允许 `document`/`window` |

`npm run typecheck` 就是把两份各跑一遍 `tsc --noEmit`。**如果某代码在错误的环境 import 了错误的东西（比如渲染层 import node:fs），typecheck 会当场红**——这是本项目最重要的自动化质量闸门。

## 5. .npmrc 与安装

`.npmrc` 已配置：
- `legacy-peer-deps=true`（规避 React 19 与部分包的 peer 声明冲突）
- 国内镜像源

所以新人只需 `npm install` 裸装，无需任何额外参数。

## 6. 日常命令与排错入口

| 命令 | 发生什么 |
|---|---|
| `npm run dev` | 起 renderer dev server → 编译 main/preload → 拉起 Electron 窗口；改 src/ 热更新，改 electron/ 自动重启 App |
| `npm run typecheck` | 两份 tsconfig 各查一遍类型 |
| `npm run build` | 三入口产出 out/ |
| `npm run smoke` | build 后以 `--smoke` 参数启动（冒烟自检） |

排错时先看**主进程控制台**（跑 dev 的终端）：scheduler 日志、LLM 错误、DB 报错都打在那里；渲染层的 console 要开 DevTools（默认没开快捷键的话，可临时在 main.ts 加 `win.webContents.openDevTools()`）。

## 7. 新人练习

1. 跑 `npm run typecheck`，确认全绿。
2. 打开 `src/shared/types.ts` 数一数：多少个 interface 是"数据库行形状"（MottoRecord/WikiEntry/...）？它们在 `api.d.ts` 里又出现了一遍——想想为什么会有两份（提示：shared/types 服务主进程，api.d.ts 服务渲染层，历史演进产物，09 篇会讨论这个技术债）。
3. 在 `electron.vite.config.ts` 里找到 `@` 别名，然后在任意模块文件里确认 `import ... from '../../components/...'` 其实可以写成 `@/components/...`（当前代码大多用相对路径，别名是留给未来用的）。
