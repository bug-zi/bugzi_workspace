# 02 - 技术栈与工程结构

> 目标：知道每个依赖为什么在 package.json 里，目录按什么逻辑分，日常命令与打包发版背后发生什么。

## 1. 技术选型一览

### 基座（立项就定下的）

| 技术 | 版本 | 用途 | 为什么选它 |

| 依赖 | 雇主功能 | 说明 |

选型态度没变：**能用平台内置的不引第三方，能少一层抽象就少一层**；但每个重功能（阅读器/终端/画布）到来时，都选了该领域的事实标准库而不是手搓。

### 分层的核心原则

**按「进程」分，再按「职责」分**：

- 第一刀：`electron/` vs `src/` —— **进程边界**，也是**能力边界**（能不能碰文件系统/shell）。
- 第二刀：主进程内 `db/`（数据）→ `services/`+`ai/`（业务）→ `ipc.ts`（接口层）；渲染层内 `theme/`+`components/`+`services/`+`hooks/`（横切）→ `modules/`（纵切业务）。
- `src/shared/types.ts` 是**唯一**同时被两个进程 import 的文件——类型与常量（`ModuleId`/`SettingsKeys`/`ErrCode`/`LLM_SCENE_LABELS`…）放这里，保证两端对齐。
- **主进程复杂业务不堆在 ipc.ts**：书籍/收藏/信息源/账本/音乐/挑战等领域服务各有独立文件，ipc.ts 只做参数接发；AI 编排集中在 `ai/services.ts`。

### 为什么渲染层没有 repository 层

模块组件直接调 `window.api.xxx.list()`，没有再包一层。因为 preload 本身已经是"类型化 API 客户端"，再包一层纯属转发。唯一的"准数据层"是 `learnGenQueue`——它管的不是数据而是**生成任务并发**，那是真正的状态机，值得独立成文件。

## 3. 构建与打包

`electron.vite.config.ts` 定义三个独立构建入口：

```
main:     entry: electron/main.ts     → out/main/main.js     （Node 环境）
preload:  entry: electron/preload.ts  → out/preload/preload.js（沙箱受限环境）
renderer: root: src/                  → out/renderer/        （浏览器环境，React 插件 + @ 别名）
```

package.json 的 `main` 指向 `out/main/main.js`——Electron 启动的就是它。开发时 renderer 跑成 dev server，主进程经 `ELECTRON_RENDERER_URL` 感知（`main.ts` 的 `createWindow()`）。

`electron-builder.yml` 打包要点（`npm run dist` 产出 NSIS 安装包到 release/）：

- `publish: github`（owner `bug-zi`，repo `bugzi_workspace`）→ 打包自动产出 `latest.yml` + `.blockmap`，应用内更新与 GitHub Releases 都靠它们。
- `npmRebuild: false` + `asarUnpack: '**/node_modules/node-pty/**'`——node-pty 自带 N-API 预编译，跳过源码重编（winpty 的 gyp 在 Windows 必失败），且原生模块必须解包到 asar 外。
- `extraResources` 把 `resources/app.png` 复制为 `<resources>/app.png`——打包态窗口/托盘图标路径（`main.ts` 的 `appIcon`）。
- NSIS：非一键安装、可选目录、总是建桌面快捷方式；`artifactName: bugzi-workspace-Setup-${version}.${ext}`。

发版流程（开发者手动）：改 package.json 版本 → `npm run dist` → `gh release create` 挂 tag 上传产物；updater 只认 `latest.yml` 里的 version。

## 4. 双 tsconfig 的原因

主进程和渲染层的**运行环境完全不同**：

| | tsconfig.node.json | tsconfig.web.json |
|---|---|---|
| 覆盖 | electron/**, src/shared/ | src/**, electron/preload.ts |
| lib | Node 全家桶 | DOM 全家桶 |
| 意义 | 允许 `node:fs`/`node:sqlite`/`node:pty` | 允许 `document`/`window` |

`npm run typecheck` 把两份各跑一遍 `tsc --noEmit`。**渲染层 import 了 node:fs 这类错位会当场红**——本项目最重要的自动化质量闸门。

## 5. .npmrc 与安装

`.npmrc` 已配置 `legacy-peer-deps=true`（规避 React 19 与部分包的 peer 声明冲突）+ 国内镜像源。新人 `npm install` 裸装即可。

## 6. 日常命令与排错入口

| 命令 | 发生什么 |
|---|---|
| `npm run dev` | 起 renderer dev server → 编译 main/preload → 拉起 Electron；改 src/ 热更新，改 electron/ 自动重启 App |
| `npm run typecheck` | 两份 tsconfig 各查一遍类型 |
| `npm run build` | 三入口产出 out/ |
| `npm run smoke` | build 后以 `--smoke` 参数启动（冒烟自检） |
| `npm run dist` | 清 release/ → 构建 → electron-builder 出 NSIS 安装包 |

排错先看**跑 dev 的终端**（主进程控制台）：`[scheduler]` 泵/定时日志、`[llm]` 记账告警、DB 报错都打在那里；渲染层 console 开 DevTools 看。

## 7. 新人练习

1. 跑 `npm run typecheck` 确认全绿；然后故意在某个 `src/modules/` 文件里 `import { readFileSync } from 'node:fs'`，看双 tsconfig 哪一边红。
2. 打开 `src/shared/types.ts`：找到 `SettingsKeys` 数一数现在有多少个键（每个键几乎都能在 `SettingsKeys` 注释里找到立项来源——DB vN 或日期）；再看 `LLM_SCENE_LABELS`——这就是全项目所有 AI 场景的索引。
3. 对照 `electron-builder.yml` 和 `package.json`：解释为什么 `dist` 前要删 release/ 目录（`predist` 钩子），以及 asarUnpack 里为什么只有 node-pty 一项。
