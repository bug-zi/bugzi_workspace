# 08 - 六大模块走读

> 目标：逐模块过关键交互与数据流，作为前七篇的综合运用。每节给出「入口文件 + 核心状态机 + 值得学的一处 + 已知毛边」。个人中心因多为表单细节从简。

## 1. 格言库（MottosModule.tsx，402 行，最大的模块组件）

### 状态机与数据流

```
mottos[]（全量三区一次拉回，前端 filter 分区）
  ├─ 分区渲染：ZONES.map → items = mottos.filter(status===z.status)
  ├─ 区折叠：collapsed: Record<'draft'|'settled'|'formal', boolean>
  └─ 行操作：
       草稿区行  → [加入沉淀区] setStatus(id,'settled')
       沉淀区行  → [加入正式区] setStatus(id,'formal')   ← 主进程此时建笔记 md！
       正式区行  → 点击开 MdDialog(note_path)；[编辑]弹表单
       通用      → [丢弃] → ConfirmDialog → item:discard
```

### 「加入正式区」的主进程逻辑（ipc.ts:183-194）

```ts
if (status === 'formal' && !row.note_path) {        // 只有没笔记的才建
  notePath = `md/mottos/${id}.md`
  UPDATE mottos SET note_path = ?
  mdCreate(notePath, `# ${content}\n\n> ${source}\n`)   // 模板：标题+引用出处
}
UPDATE mottos SET status = ?
```

**状态升级的副作用（建笔记）在主进程原子完成**——渲染层只管 setStatus 一次调用。对比手动新增正式区格言（mottos:create，ipc.ts:163-178）同样内联建笔记，逻辑一致。

### 值得学的一处：批量导入的解析与前端查重（MottosModule.tsx:102-123）

```
每行 match /^(.+?)\s*——\s*(.+)$/   ← 「格言 —— 出处」格式，无分隔则出处空
查重集合 = mottos.map(m => m.content.replace(/\s/g,''))   ← 仅去空白，比主进程 normalizeText 宽松
逐条 await create(...)            ← 循环串行 IPC（N 条 N 次往返，量小可接受）
toast 报「共 X 条，去重后导入 Y 条」
```

注意这里的查重是**渲染层宽松版**（去空白）与主进程入库时不查重的组合——手动路径的查重责任在前端，AI 路径的查重责任在主进程（normalizeText）。两条入口两套防线，精度不同。

### 已知毛边

- `mottos:normalize` 通道（preload 有暴露）当前无 UI 消费——是给前端做同款查重的预留，未接线。
- 生成中用户可以切走模块再切回来，`generating` state 仍在（组件未卸载），但若切走时模块卸载…… 实际不卸载（条件渲染切换会卸载！）——切走再切回 `generating` 已重置，若那次 invoke 仍在飞行，回来后 toast 不会弹（state 已丢）。低危但真实。

## 2. 万象库（WikiModule.tsx，最复杂的导航）

### 三视图判别联合

```ts
type View = { kind: 'overview' } | { kind: 'section'; id: number } | { kind: 'notebook' }
```

比"三个布尔"或"字符串+id 两个 state"都稳：**kind 与 id 绑定在同一个对象里，不可能出现 section 视图配错 id**。这是 TS 判别联合在 UI 导航上的教科书用法，值得抄。

### 数据加载的分层

```
loadSections()        板块 + 各板块词条数（counts，串行 N 次 entries() 拿 length）
loadHighlights()      笔记本高光列表
view.kind==='section' → loadEntries(view.id)     依赖 [view, mdVersion]
```

`mdVersion` 计数器：卡片弹窗内每次 md 变更（编辑/划词高光）+1，触发所在板块词条列表刷新（summary 可能变了）。

### 生成流程的三个出口（WikiModule.tsx:98-124）

```
runGenerate(term, sectionId)
  → r.ok === true   → toast + 打开新卡片弹窗
  → r.ok === false  → conflictTerm 弹「已存在」框 → [查看原卡片]（conflictEntry 定位跳转）
  → throw           → LLM_NOT_CONFIGURED / MCP_NOT_ENABLED / 其他 → 三种弹窗
```

三出口模式（成功/业务冲突/异常）在本模块最完整。

### 划词高光的落库细节（WikiModule.tsx:127-148）

```
读 md 原文
  已含 ==text==   → 只补 highlights 表记录
  含裸 text       → md.replace(text, '==text==') 写回 + 补记录
  都不含          → 只补记录（说明 md 被改过选区对不上）
```

高光 = **md 内联标记 + DB 记录双写**。md 里的 ==标记== 让你在原文语境看到高亮；wiki_highlights 表让笔记本板块能聚合列出所有高光（JOIN 词条名）。渲染侧 MdDialog 把 ==x== 后处理成 <mark>。

### 已知毛边

`md.replace(text, wrapped)` 只替换**第一处**出现——若词条文里该词多次出现，只高第一次（可接受）但若选的是第二次出现的上下文，replace 仍会标记第一处（轻微错位，肉眼难察觉级别）。

## 3. 灵感泉（InspirationsModule.tsx）—— 纯前端交互最重的模块

### 拖拽三场景

```
onDragStart     记 dragIdRef + dataTransfer.setData('text/plain', id)
onDropToZone    拖到空区 → moveTo(item, status)：sort = 目标区 max+1
onDropToCard    拖到某卡上 → sort = target.sort - 0.5（插中缝）→ normalizeSort(该区)
```

`onDropToCard` 的跨区分支：拖到**别区某张卡**上 = 移到该区并插在那张卡前。drop 后 `normalizeSort` 把浮点中缝重编整数（InspModule.tsx:99-105），随后 `inspirations:reorder` 批量 UPDATE。

**毛边预警**：normalizeSort 读的是 `items`（拖放前的快照），它 filter 出的"该区卡片"不含刚 move 的源卡——move 已经单独发了，normalize 覆盖的是目标区其余卡。顺序正确性依赖"move 先落库、normalize 后覆盖且不动源卡"的时序，能工作但重排窗口期两次全量写。重构练习的好素材。

### 新建灵感即建 md（ipc.ts:260-270）

title/status 先插（md_path='PENDING'）→ 拿 id → 回填 `md/inspirations/<id>.md` + mdCreate(`# ${title}\n`)。与格言笔记的差异：灵感**任何区**都有文档（格言只有正式区有笔记）——因为灵感的价值本体就是那个文档，格言的价值本体是那句话。

## 4. 辩真阁（VerifyModule.tsx）

### 提交前查重的三选一（VerifyModule.tsx:48-58 + 169-202）

```
runVerify(text)
  → findDuplicate(text)    主进程全表拉回逐条 normalizeText 比对
  → 命中 → dupInfo 弹窗：[关闭] / [查看旧记录]（dupEntry 开 MdDialog）/ [重新验证]
  → 未命中 → doVerify(text)
```

`verify:findDuplicate`（ipc.ts:294-298）与格言 AI 查重共用 normalizeText——**同一把"相等"的尺子**量两种场景（库内去重 / 重复提交拦截）。

### 过程直播的接线（本模块最精巧）

```
doVerify → props.onOpenAi()（先展开边栏）
        → invoke verify:run
主进程 runVerification(claim, msg => pushAiSystemMessage(msg))
        → ai_messages 落库 + webContents.send('ai:message')
渲染层两处同时收到：
  VerifyModule 自己订阅 onMessage → aiVersion+1 → bumpAi() → Shell → AiSidebar 重载
  AiSidebar 自己也订阅 onMessage → 也重载
（双订阅冗余但无害——都是全量重拉，幂等）
```

### 可信度徽章分级

`cred-badge high(≥70)/mid(≥40)/low` 三档配色（RecycleModule 式的规则化 UI）。70/40 是产品定的直觉分界，无统计依据——**魔法数字要有，但要知道它是产品判断不是工程推导**。

## 5. 回收站（RecycleModule.tsx）

### 广播消费闭环

```
任意模块 discard → 主进程 recycle:changed 广播
  → RecycleModule 的 onRecycleChanged 订阅 → version+1 → useEffect 里 load()
```

version 计数而非直接 load 的原因：订阅回调里 setState 触发 effect 是 React 里最稳的"异步事件→重拉"路径（避免在事件回调里直接 await 造成竞态）。

### 纯派生展示逻辑

`summaryOf(payload)`（JSON.parse 快照取 content/term/title/claim）、`remainText`（3天-elapsed → 「剩N天/今天到期/即将清理」）。**回收站零自有数据，全是派生视图**——这就是 05 篇"快照自治"设计在 UI 侧的红利。

## 6. 个人中心（ProfileModule.tsx + WelcomeGuide.tsx）

### 三块配置的持久化模式

- 用户信息：settings 三 key（user_name/user_avatar/user_bio），头像走 `image:pick`（主进程对话框→拷贝到 userData→清旧扩展名文件→记 settings）。
- 字体：settings 三 key → ThemeProvider.applyFontVars 即时生效。
- LLM：**多套配置**存 `llm_configs`（JSON 数组）+ `llm_default_id`；每套可「测试连接」（llm:test，max_tokens:1 探活）。
- MCP：`mcp_configs` 数组 + 每项 enabled 开关；v1 仅 HTTP 传输。

### WelcomeGuide 的定位

由 `firstLaunch`（= 无 user_name）驱动；完成引导=填了用户名。步骤：用户名 → 主题 → LLM 提示（可跳过）。**引导的完成标记就是业务数据本身**，没有 guide_done 冗余 key——少一个状态就少一种不同步。

## 8. 新人练习（走读验收）

1. 不看代码回答：格言从 AI 生成到出现在正式区列表，最少要经过几次用户操作、几次状态变更？（答：AI 生成→草稿；用户点沉淀→settled；用户点正式→formal+建笔记。两次点击，两次 UPDATE，一次 mdCreate。）
2. 把万象库的 `View` 类型改成三个布尔会出什么问题？构造一个具体 bug 场景。（提示：section 页停留时点开笔记本再返回——id 与 kind 脱钩的时序。）
3. 实验体验"广播"：开着回收站页签，去格言库丢一条格言，观察回收站页数字即时 +1；然后解释这背后的两条消息路径（recycle:changed 广播 + 你丢完自己 load 的那条不相关——回收站刷新只靠前者）。
