# 09 - 定时任务与设计权衡

> 目标：理解 scheduler 的实现机制与"错过即跳过"的产品哲学；盘点全项目的设计决策、技术债与改进方向。这是收官篇，也是"如果你要接手开发"的交接篇。

## 1. 定时任务（electron/services/scheduler.ts）

### 两个任务

| 任务 | 触发 | 动作 |
|---|---|---|
| 格言定时生成 | 每天用户设定时刻（默认 22:00，settings.motto_schedule） | generateMottos() + 记 last_motto_run |
| 回收站清理 | 每天零点（00:00:05）+ App 启动时 | cleanupExpired()（3 天超期彻底删） |

### 实现机制：setTimeout 链

```ts
export function scheduleMottoTask(): void {
  if (mottoTimer) clearTimeout(mottoTimer)
  const delay = msUntilNext(schedule)      // 距下一个 HH:mm 的毫秒数
  mottoTimer = setTimeout(() => {
    void runScheduledMottos()
    scheduleMottoTask()                    // ← 执行完自重排（跨天滚动）
  }, delay)
  mottoTimer.unref?.()                     // ← 不阻止进程退出
}
```

三个技术点：

1. **msUntilNext（scheduler.ts:12-20）**：构造今天的目标时刻，`<= now` 就 +1 天——天然处理"已过今天 22 点要排明天"的边界。
2. **自重排递归**：每次到点执行完立刻排下一个。不做 `setInterval`（会漂移、改设置难清理）。
3. **unref()**：定时器不阻止 Node 退出——App 关闭时不会被挂起的 timer 拖住不退。`?.` 是因为个别环境类型差异的防御写法。

**改设置即重排**：`settings:set` 通道里发现 key 是 motto_schedule 就调 scheduleMottoTask（ipc.ts:41-43）——clearTimeout 旧的排新的，立即生效。

### 「错过即跳过」的幂等实现（scheduler.ts:30-41, 57-68）

规则 8 说 App 未运行时错过就跳过、**不补生成**。实现：

```ts
function alreadyRanToday(): boolean {
  const last = getSetting('last_motto_run')
  // last 的本地年月日 === 今天的本地年月日 → 今天跑过了
}
```

启动时 scheduleMottoTask 排的必然是**未来**时刻（msUntilNext 的 +1 天逻辑），所以"错过"场景天然不会触发补跑；`alreadyRanToday` 防的是另一件事：**同一天内 22:00 后用户改设置成 21:00 并重启 App**——msUntilNext 排明天 21 点没问题；而如果排程逻辑未来改成"启动即检查补跑"，这个标记就是防重复生成的闸。它同时被 runScheduledMottos 执行前检查（双保险）。

### 静默失败哲学（scheduler.ts:57-68）

```ts
catch (e) {
  console.warn(`[scheduler] 定时格言生成失败：${...}`)   // 只打日志
}
```

注释写明"LLM 未配置也静默（定时任务不弹窗）"。**后台任务的错误不打扰用户**——用户晚上没开 LLM，不能半夜弹个错误框。代价是失败了无人知晓（除非看日志）。这是"定时生成"与手动点按钮（会弹引导/失败框）的刻意体验分岔。

### 零点清理的 5 秒偏移

`msUntilMidnight` 目标是 `次日 00:00:05`——避开零点整的系统级任务高峰（也避开多服务同时触发的习惯时刻），5 秒偏移是老派系统编程的礼貌。

### 局限（诚实清单）

- setTimeout 在系统休眠时的行为：Windows 唤醒后 timer 继续按剩余时间走，长时间休眠可能"补触发"——此时 alreadyRanToday 会挡住当天重复，实际安全。
- 没有持久化"下次触发点"，全部现算——因为规则本来就是"错过拉倒"，无需持久调度队列。**简单性来自产品规则的宽容**。

## 2. 设计权衡盘点（为什么它是这个样子）

| 决策 | 备选方案 | 为什么选现在这个 |
|---|---|---|
| node:sqlite 而非 better-sqlite3 | 引第三方（需原生编译） | Node 内置零依赖，Windows 免编译坑；代价是 API 较新、无同步事务封装 |
| 全量拉取+setState 而非虚拟化/增量 | React Query/无限滚动 | 个人数据量级（百~千行）下全量是正确复杂度 |
| 回收站软删+快照双写 | 仅软删/仅快照 | 软删保恢复零成本，快照保回收站自治显示 |
| md 存真实文件而非 DB BLOB | 全 DB | 用户可以用任何编辑器直接打开自己的笔记；md 生态可迁移 |
| LLM JSON 用 prompt 约定+剥围栏 | jsonMode 一把梭 | jsonMode 不是所有兼容端都支持，剥围栏解析兼容面最大 |
| 无状态库 | Redux/Zustand | 模块间几乎无共享状态；唯一的协调（边栏）靠 Shell props |
| IPC 手工镜像类型（preload/api.d.ts） | 自动推导 | tsconfig 进程边界隔离下自动推导需引 electron 类型进渲染层，当时嫌重（见技术债#1） |
| 弹窗=state 条件渲染 | 路由/Portal 管理 | 声明式最直白；弹窗无叠层需求 |
| `bzres://` 协议 | file:// 或 base64 | 安全（锁死 userData）+ 可缓存 + fetch 可探测 |

## 3. 技术债与已知问题（接手开发先读）

按优先级排：

1. **preload/api.d.ts 双份类型手工同步**——每加通道要改两处，漏了就是运行时才炸的类型漂移。修法：渲染层 tsconfig.web.json 把 `electron/preload.ts` 纳入 include 并 `import type { Api }`，或用 d.ts 生成脚本。**改动小收益大，首选还的债**。
2. **无事务包裹**——discard 的软删+快照双写、verify 的插入+回填+写 md 都是两步写，断电留半成品。修法：这些函数包 `BEGIN IMMEDIATE ... COMMIT`（node:sqlite 支持 `db.exec`）。
3. **`shared/types.ts` 与 `api.d.ts` 的行类型重复定义**（MottoRecord 等两份）——同源不同步风险。修法与债 1 一起做：统一从 shared 导入。
4. **主进程无重入防护**——`mottos:generate` 前端有 `generating` 挡连点，但 IPC 层谁都能再 invoke（如未来多窗口）。修法：主进程模块级 in-flight 标记。
5. **VerifyModule 的 effect 依赖 `props` 对象**（08 篇提过）——功能正确但每次渲染都跑 effect。修法：解构 `props.bumpAi` 进依赖。
6. **md.replace 高光首处匹配**、**灵感拖拽 normalizeSort 时序依赖**——低危正确性毛边，重构时顺手修。
7. **ai_messages 无限增长**——v1 单会话全历史不清理，aiChat 每次取最近 30 条构造上下文，但表会一直涨。产品上有意（"持久保存"），工程上可在 v2 加"仅保留上下文所需"或导出功能。

## 4. 扩展路线建议（如果继续开发）

- **加新模块**的最小改动面已画过（01 篇练习）；真正的工程化改进是先还债 1/3，让"加通道"从改 4 个文件降到 2 个。
- **LLM 流式输出**：chatCompletion 加 stream:true + SSE 解析（MCP 的 parseSseResponse 可复用思路），边栏体验提升最明显的单项。
- **多会话**：ai_messages 加 session_id 列（迁移 version 2），边栏加上会话切换——数据模型预留成本低。
- **导出/备份**：userData 目录整体拷贝即完整备份（DB+md 全在里面）——这个性质要在文档里明示给用户。

## 5. 给接手者的最后三句话

1. **先读 specs 再改代码**：代码里每个 `specs §x.y` 注释都是需求回溯锚点，改行为前先看 specs 说了什么，是"实现偏差"还是"需求就该这样"。
2. **改主进程记得 typecheck 两遍都能过**：`npm run typecheck` 是唯一自动闸门，别绕过。
3. **所有新交互先过"宪法"**：删除有确认吗？图标是 Material Symbols 吗？颜色走变量吗？按钮没配置时弹引导而不是置灰吗？——这四问答不上来就别提 PR。

## 6. 结业练习（综合）

实现一个小需求走完全链路：**给格言库正式区加"随机展示一条"的顶栏按钮**。

要求：
- 图标用 `casino`（Material Symbols），禁 emoji；
- 点击后 MdDialog 打开该格言笔记（复用现有 viewId 状态即可）；
- 思考：纯前端能实现（列表已在手）还是要加 IPC？（答：纯前端，`mottos.filter(formal)` 随机取一）；
- 做完后自查：这个功能需要二次确认吗（否——非破坏性操作）、需要去配置引导吗（否——不碰 LLM）。

如果你能独立完成并答对两个"否"，这套笔记的使命就完成了。
