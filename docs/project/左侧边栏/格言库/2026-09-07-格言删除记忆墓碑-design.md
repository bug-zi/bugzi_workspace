- **关联**：第 23 轮（句式约束，同为 generateMottos 管线改造；其「命中剔除不补足」在本轮升级为统一补足一轮）

## 背景与问题

`generateMottos()`（electron/ai/services.ts）的查重本已是双保险，且**覆盖回收站**：

1. prompt 侧避免清单 = `SELECT content FROM mottos ORDER BY updated_at DESC LIMIT 500`，不过滤 `deleted_at`——软删行也在清单内；
2. 代码侧入库判重（`isDupMotto`：规范化一致或互为子串 ≥6 字）比对集合同样含软删行，且有批内互斥。

因此格言躺在回收站的 3 天内不会被重复生成。**真正的记忆空洞在「彻底删除」**——行从 mottos 表物理 DELETE，一切查重依据归零：

| 用户路径 | 代码位置 |
|---|---|
| 回收站手动「彻底删除」 | recycle.ts `hardDelete`（模板 SQL） |
| 回收站 3 天自动清理 | recycle.ts `cleanupExpired` → 复用 `hardDelete` |
| 格言库模块内「直接删除」 | ipc.ts `mottos:deleteForever` |

（grep 核实：全项目物理删除 mottos 仅上述两处代码。）摘录条是真实名句、池子小，删掉之后数日再生成时极易原样复现。方案：建「墓碑表」在物理删除时留底，生成管线两端接入；经探讨否决「双标记软删」（侵入全部 mottos 查询）与「settings 存清单」（丢代码侧判重）。

## 三项已确认决策

1. **场景定位 = 彻底删除之后**（开发者确认）：墓碑只挂物理删除钩子；软删期间已有双保险覆盖，恢复路径不写墓碑。
2. **补足策略 = 统一补一轮**：第一轮入库后若有剔除——不管因墓碑重复/库内重复/句式违规——按缺口配比再调一次 LLM 补足，重跑同一套过滤后入库，到此为止。语义统一为「尽量交付满 10 条，最多两轮」，不做无上限循环。
3. **保留窗口 = 永久留底 + prompt 注入限量**：墓碑表只增不删（人手删除频率下量级极小，零维护）；代码侧判重查全量，prompt 注入只取最近 300 条控制 token。

## 实施方案

### 1. 数据结构（DB v16）

```sql
CREATE TABLE motto_tombstones (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  content TEXT NOT NULL,        -- 原文（prompt 注入用）
  content_norm TEXT NOT NULL,   -- 写入时预计算 normalizeText（判重用）
  created_at TEXT NOT NULL
)
```

- 不建索引、无定时清理——几千行封顶，全表扫描毫秒级。
- 写入时轻量去重：`content_norm` 已存在则跳过（防「手动加回同一句再删」堆积重复行、prompt 里出现两遍）。

### 2. 写入路径（db.ts 新增 + 两处钩子）

`db.ts` 新增 `recordMottoTombstone(content: string)`（含 norm 去重查询），两个删除点在 **DELETE 之前**调用（保证 content 在手）：

| 用户路径 | 钩子位置 | 改动 |
|---|---|---|
| 回收站「彻底删除」/ 3 天自动清理 | recycle.ts `hardDelete` mottos 分支 | 现查询只取 note_path，扩为 content + note_path，删行前写墓碑 |
| 模块内「直接删除」 | ipc.ts `mottos:deleteForever` | 同样先查 content 写墓碑再 DELETE |

### 3. 生成管线（generateMottos）

**prompt 侧**：现有「已有格言清单」段之后追加独立段（最近 300 条墓碑，与 500 条避免清单各自独立、互不挤占）：

```
以下是我明确删除过的格言，同样不得生成，也不得仅差微小改写：
${tombstoneList}
```

**代码侧**：全量墓碑 `content_norm` 并入 `allNorms`，复用 `isDupMotto`，判重口径与库内完全同构。

**入库循环**：判重先查墓碑集合、再查库内集合——区分 `tombstoneRejected` 与库内重复两种计数，两者连同句式违规都计入补足缺口。

**补足轮**：

- 缺口按 5/5 配比：`shortfallE = max(0, 5 - excerptInserted)`、`shortfallC = max(0, 5 - composedInserted)`，两者均 ≤0 不补。
- prompt 复用同一模板参数化（生成条数换成「恰好 X 条摘录 + Y 条编撰」，避免清单追加本批已入库条目），解析容错重试同第一轮。
- 补足产物重跑同一套过滤（墓碑 + 库内 + 批内 + 句式）后入库，**无第二轮**。
- 补足调用/解析失败**非致命**：保留第一轮结果照常返回。

**计数**：`GenerateMottosResult` 增 `tombstoneRejected`（两轮合计命中墓碑剔除数）、`supplemented`（补足轮最终入库数）；`generated` = 两轮 LLM 返回条数之和，`inserted`/`excerptInserted`/`composedInserted`/`patternRejected` = 两轮合计。preload / api.d.ts 透传同步。

### 4. UI 与文案

无新界面。MottosModule 生成完成 toast 扩展：

```
本次生成 X 条（摘录 A + 编撰 B），去重后入库 N 条
  [+ ，其中 M 条为补足生成]       （supplemented > 0 时）
  [+ ，K 条与已删除格言重复已剔除]  （tombstoneRejected > 0 时）
  [+ ，P 条因句式违规未入库]        （patternRejected > 0 时，现状保留）
```

定时生成（每晚 10 点）走同一 IPC `mottos:generate`，自动受益。

## 明确不做的事

- **手动新增不判墓碑**——墓碑只约束 AI 生成，手动加回同一句是用户自由。
- 不做模糊相似度匹配——沿用 `isDupMotto`（规范化一致/互为子串 ≥6 字）口径，不新发明。
- 不做双标记软删（purged 行侵入全部现有 mottos 查询）、不做 settings 存清单。
- 墓碑表不做用户可见界面、不做手动清空。
- 补足最多一轮，不循环到满 10。
- AI 超配返回（如 7 摘录 + 5 编撰全入库）时照常全收、不回收多出条目——继承现状入库循环行为，补足只填缺口不削超额。

## 验证

- `npm run typecheck` 通过。
- 冒烟清单：
  1. 三个删除路径各删一条 → `motto_tombstones` 出现对应行；同一句删两次不产生重复行。
  2. 彻底删除一条正式区格言原句 → 「来10条格言」→ 该句不重现。
  3. 构造补足场景（如删除库内高频名句后生成）→ toast 出现「补足生成」/「已删除格言重复剔除」计数，总入库尽量为 10。
  4. 断网或 LLM 失败时补足轮非致命，第一轮结果正常返回。
